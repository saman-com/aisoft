## 1. Goal

Build a reliable, semi-autonomous workflow where:

1. The **Pi agent** (local coding agent) writes or improves code.
2. Pi creates and pushes a Pull Request.
3. **PR-Agent** (running in GitHub Actions via OpenRouter) automatically reviews the PR.
4. Pi enters a monitoring + fixing loop:
   - Reads the PR-Agent review
   - Extracts a Confidence Score (0–5)
   - Extracts the list of issues and a ready-to-use Agent Prompt
   - If score < 5 → uses the Agent Prompt to fix the issues, pushes, and repeats
5. The loop stops when the review is good enough (**5/5**, or **4/5** with no P0/P1
   issue) or after a maximum of **5 iterations**.
6. A human performs the final merge.

The system prioritizes:
- Low cost (OpenRouter + local Pi)
- Clear structure and observability
- Safety (human always controls the final merge)
- Easy iteration and debugging

## 2. High-Level Architecture

```

│         Local Machine       │
│                             │
│  ┌─────────────┐            │
│  │  Pi Agent   │◄───────────┼─── Driver Script / Pi Skill
│  └──────┬──────┘            │
│         │ writes code       │
│         │ creates PR        │
│         │ monitors & fixes  │
└─────────┼───────────────────┘
          │
          │ git push / gh CLI
          ▼
┌─────────────────────────────┐
│         GitHub              │
│                             │
│  Pull Request               │
│         │                   │
│         ▼                   │
│  GitHub Action              │
│  (PR-Agent + OpenRouter)    │
│         │                   │
│         ▼                   │

│  - Confidence Score X/5     │
│  - Issues list              │
│  - Agent Prompt             │
└─────────────────────────────┘
```

### Key Principles

- **PR-Agent** only runs in GitHub Actions (cloud).
- **Pi agent** only runs locally.
- Communication happens through the Pull Request comments and Git.
- The driver script (or Pi skill) owns the control loop.

## 3. Components

### 3.1 GitHub Action – PR-Agent Reviewer

**File:** `.github/workflows/pr-agent.yml`

**Responsibilities:**
- Trigger on PR `opened`, `synchronize`, `reopened`
- Run PR-Agent using OpenRouter
- Force structured output containing:
  - Confidence Score (0–5)
  - Issues list
  - Agent Prompt (ready for Pi)

**Key configuration:**
- Model via OpenRouter (e.g. Claude Sonnet, GPT-4o, DeepSeek, etc.)
- `require_score_review = true`
- Custom `extra_instructions` that force the exact output format

### 3.2 Repository Configuration

**File:** `.pr_agent.toml` (in repo root)

Contains:
- Model selection
- Forced score + risk + merge recommendation sections
- Strict output format instructions so the review is machine-parseable

### 3.3 Local Driver / Pi Skill

**Responsibilities:**
1. Detect or create the current PR for the branch
2. Wait for the latest PR-Agent review comment
3. Parse:
   - Confidence Score (`X/5`)
   - Issues list
   - Agent Prompt section
4. Decision logic:
   - Score == 5 → stop and notify human
   - Score >= 4 with no P0/P1 issue → stop and notify human (the reviewer
     plateaus at 4/5 while listing findings it rates as minor; see PR #27)
   - Otherwise, iterations < 5 → feed Agent Prompt to Pi → commit & push → repeat
   - Otherwise → stop and notify human that the limit was reached
5. Enforce max 5 iterations
6. Provide clear terminal feedback at every step

### 3.4 Pi Agent

- Receives the Agent Prompt generated by PR-Agent
- Makes the minimal necessary code changes
- Commits with a clear message
- Pushes to the same branch (which re-triggers the GitHub Action)

## 4. Detailed Flow

### Phase A – Initial Creation

1. Developer (or Pi) works on a feature branch.
2. Pi finishes the implementation.
3. Driver script runs:
   ```bash
   python3 scripts/driver_pr.py --create
   ```
   or detects an existing open PR.
4. Push triggers the GitHub Action → PR-Agent starts reviewing.

Creation is `driver_pr.create_pull_request`, and it does two things beyond
calling `gh pr create`:

- **It looks first.** The branch is checked for an open PR before creating one,
  because two PRs on one branch means two review runs and two loops fixing the
  same code, with no cheap undo. When one exists it raises `PullRequestExists`
  carrying the PR it found; reusing that PR instead of refusing is T5.2.
- **It writes the title and body from git.** The title is the newest commit
  subject, or the branch name when the branch has no commits ahead of the base.
  The body names the branches and lists the commits the base does not have. Both
  are derived, so neither can contradict the diff.

A `gh pr create` failure is raised with gh's own message rather than mapped to a
status code, because the reasons (branch not pushed, no commits between the
branches, no permission) are each fixed differently.

### Phase B – Review Loop (max 5 iterations)

```
iteration = 0
while iteration < 5:
    1. Wait for PR-Agent comment to appear / update
       (poll every 15–30 seconds, timeout after ~10 minutes)

    2. Parse the latest review comment:
       - Extract "## Confidence Score" → integer 0–5
       - Extract "## Issues"
       - Extract "## Agent Prompt"

    3. if score == 5, or score >= 4 with no blocking issue:
          print("✅ ready for human merge")
          exit success

    4. otherwise, if iterations remain:
          print(f"Score {score}/5 – fixing issues (iteration {iteration+1}/5)")
          Feed the full "Agent Prompt" to Pi
          Pi edits files
          git add -A
          git commit -m "fix: address PR-Agent feedback (iteration N)"
          git push
          iteration += 1
          continue

    5. if no new review appears or parsing fails:
          abort with clear error
```

### Phase C – Human Merge

- When the review is good enough (5/5, or 4/5 with nothing blocking) or max
  iterations are reached, the driver stops.
- Human reviews the final state and merges the PR.

## 5. Output Contract (Critical)

PR-Agent **must** always produce this exact structure at the end of its review comment:

```markdown
## Confidence Score
4/5

## Issues
- [P1] src/auth.ts:42 — Missing null check on user object
- [P2] src/api.ts:18 — Potential N+1 query

## Agent Prompt
Fix the following issues in the current PR. Make the minimal correct changes while preserving existing style and tests:

1. In src/auth.ts around line 42, add a null check for the user object before accessing its properties.
2. In src/api.ts around line 18, refactor the query to avoid the N+1 problem (use a join or batch loading).

After making the changes, ensure the code still compiles and existing tests pass.
```

This contract makes parsing reliable and gives Pi a high-quality, self-contained prompt.

## 6. Configuration Details

### 6.1 GitHub Action Example

```yaml
name: PR Agent Review

on:
  pull_request:
    types: [opened, synchronize, reopened]
  issue_comment:
    types: [created]

jobs:
  review:
    if: github.event.sender.type != 'Bot'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
      issues: write

    steps:
      - name: Run PR-Agent
        uses: the-pr-agent/pr-agent@main
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          OPENROUTER__KEY: ${{ secrets.OPENROUTER_API_KEY }}
          config.model: "openrouter/anthropic/claude-sonnet-4"
          github_action_config.auto_review: "true"
          github_action_config.auto_describe: "false"
          github_action_config.auto_improve: "false"
          pr_reviewer.require_score_review: "true"
          pr_reviewer.require_risk_assessment: "true"
          pr_reviewer.require_merge_recommendation: "true"
```

### 6.2 `.pr_agent.toml` (recommended)

```toml
[config]
model = "openrouter/anthropic/claude-sonnet-4"

[pr_reviewer]
require_score_review = true
require_risk_assessment = true
require_merge_recommendation = true

extra_instructions = """
Always end your review with these three sections in this exact format and nothing after them:

## Confidence Score
X/5

## Issues
- [P0/P1/P2] path/to/file:line — short description

## Agent Prompt
A single, self-contained prompt that a coding agent can copy-paste to fix all the issues above.
Include concrete file paths and clear instructions.
Do not add any text after the Agent Prompt section.
"""
```

## 7. Local Driver Responsibilities

The driver (bash or Python) must:

- Authenticate with `gh` CLI
- Detect current branch and associated PR
- Poll for the latest comment from the PR-Agent bot
- Robustly parse the three required sections
- Invoke Pi non-interactively with the Agent Prompt
- Commit and push with a descriptive message
- Track iteration count
- Exit cleanly with clear status messages

Optional enhancements:
- Detect repeated identical issues (stop early) — implemented as `Outcome.REPEATED`
  (T4.3, see `docs/TASKS.md` for the rule and its guards)
- Support dry-run mode
- Log full conversation history
- Notify via desktop notification or Slack when score reaches 5

---

## 8. Safety & Guardrails

| Risk                        | Mitigation                                      |
|-----------------------------|-------------------------------------------------|
| Infinite loop               | Hard limit of 5 iterations                      |
| Pi makes destructive changes| Prefer minimal diffs; human reviews final state |
| Score never reaches 5       | Stop after 5 tries and hand control to human    |
| Parsing fails               | Abort with clear error + raw comment dump       |
| Cost runaway                | OpenRouter usage is per-review; monitor credits |
| Secrets exposure            | OpenRouter key only in GitHub Secrets           |

Human always retains final merge authority.

---

## 9. Success Criteria

The system is considered successful when:

1. Pi can create a PR and the GitHub Action reliably triggers.
2. PR-Agent consistently produces the three required sections.
3. The local driver can parse the score and Agent Prompt reliably.
4. The fix → push → re-review cycle works for at least 2–3 iterations.
5. When the review is good enough (5/5, or 4/5 with no P0/P1 issue), the driver
   stops and clearly notifies the user.
6. The entire loop can be observed and debugged from the terminal.

## 10. Future Extensions (Out of Scope for v1)

- Fully headless mode (no human in the loop for low-risk PRs)
- Multi-agent debate (second model reviews the first model’s fixes)
- Integration with TREX-style runtime testing
- Automatic labeling (`ready-to-merge`, `needs-human-review`)
- Slack / Discord notifications
- Support for GitLab / Bitbucket
